# SRD 版本与卡图包改造临时开发计划

## 1. 背景与目标

本次改造的核心目标是将当前项目调整为默认不包含官方相关卡图的 SRD 版本，避免默认发行包直接携带相关图片资源。同时保留用户在本地恢复原有图片体验的能力，并尽量复用现有的图片模式、文字模式和图片缓存机制。

本次改造完成后，产品应满足以下原则：

1. 默认进入时是纯文字可用版本。
2. 主程序不依赖远程图片 URL，不额外增加 Cloudflare Pages 免费版的运行压力。
3. 用户可通过导入单独的卡图包，在本地恢复图片体验。
4. 未导入卡图包时，界面明确提示当前为 SRD 版本。
5. 后续更新公告可以通过维护 Markdown 文件夹持续扩展，不再把公告内容写死在组件里。

## 2. 已确认的产品决策

### 2.1 卡图改造方向

1. 默认发行包移除所有官方相关卡图资源。
2. 不走远程 URL，不做在线下载卡图方案。
3. 用户通过导入单个 zip 文件恢复卡图。
4. zip 文件内部自带配置文件，不再要求用户额外单独选择配置文件。
5. 导入后图片落地到 IndexedDB，本地读取，不直接运行时读取 zip。
6. 原有自定义卡包导入系统保持不变，不和官方卡图包导入混用。

### 2.2 首页与模式切换

1. 首页新增“导入卡图”按钮。
2. 现有图片模式 / 文字模式切换继续保留。
3. 未导入卡图包时，图片模式按钮置灰。
4. 用户点击置灰按钮时，弹出提示，引导先导入卡图包。
5. 导入成功后，恢复可切换图片模式。

### 2.3 首次进入公告

1. 首次进入时弹出更新公告弹窗。
2. 第一条公告必须明确提示：当前是 SRD 版本，如需卡图请自行导入。
3. 后续公告维护方式改为编辑 Markdown 文件。
4. 需要维护一个公告目录，后续新增公告时只需增加或编辑 Markdown 文件。

### 2.4 版本兼容策略

1. 卡图包版本不匹配时仅警告，不阻止导入。
2. 如果重复导入卡图包，按覆盖旧包处理。
3. 需要提供清除本地卡图缓存的入口，便于回到纯文字状态。

## 3. 功能范围

### 3.1 本次要做

1. 主程序默认移除官方相关卡图资源。
2. 新增官方卡图包导入入口。
3. 新增官方卡图包导入逻辑。
4. 新增本地卡图包元信息存储。
5. 接入现有图片服务链路，支持从 IndexedDB 读取官方卡图。
6. 调整图片模式按钮状态逻辑。
7. 新增首次进入公告弹窗。
8. 新增 Markdown 公告目录与读取机制。
9. 新增“清除卡图缓存”入口。
10. 补充必要文档与测试。

### 3.2 本次不做

1. 不做远程卡图 URL 加载。
2. 不做服务端密钥校验。
3. 不改动现有自定义卡包导入协议。
4. 不引入新的后端服务。
5. 不把“公告系统”扩展成完整 CMS。

## 4. 卡图包格式设计

### 4.1 导入文件形式

用户导入一个 zip 文件，内部至少包含：

1. `manifest.json`
2. `images/`

建议结构：

```text
official-image-pack.zip
├─ manifest.json
└─ images/
   ├─ card-id-1.webp
   ├─ card-id-2.webp
   └─ ...
```

### 4.2 manifest.json 建议字段

建议最小结构如下：

```json
{
  "type": "official-image-pack",
  "packId": "builtin-official-images",
  "version": "2026-05",
  "target": "builtin-base",
  "matchBy": "cardId",
  "imagePattern": "images/{cardId}.webp"
}
```

建议说明：

1. `type`：用于识别这是卡图包，不是普通卡包。
2. `packId`：卡图包唯一标识。
3. `version`：卡图包版本号。
4. `target`：声明它服务于哪一套内置卡数据。
5. `matchBy`：当前固定为 `cardId`。
6. `imagePattern`：用于表达 zip 内部图片命名规则。

### 4.3 导入校验策略

导入时建议校验：

1. zip 中必须存在 `manifest.json`。
2. `manifest.json.type` 必须为 `official-image-pack`。
3. `matchBy` 必须为 `cardId`。
4. `images/` 下文件名应能映射到卡牌 ID。
5. 如果发现无法匹配的图片，给出警告或列表。
6. 如果版本与当前内置卡包版本不一致，只弹警告，不阻止导入。

## 5. 数据与缓存设计

### 5.1 图片存储策略

图片导入后统一写入 IndexedDB，不保留对 zip 文件的运行时依赖。

目标效果：

1. 用户导入一次后可离线使用。
2. 运行时不向 CF Pages 发起图片请求。
3. 保持当前已有的懒加载 + 缓存模型。

### 5.2 复用现有能力

优先复用当前已有链路：

1. `card/stores/image-service/actions.ts`
2. `card/stores/image-service/database.ts`
3. `lib/utils.ts` 中的图片读取函数

需要注意：

1. 现有 `.dhcb` 导入器会导入卡数据，不能直接复用为官方卡图包导入器。
2. 官方卡图包应是单独入口、单独导入逻辑。
3. 但底层的 IndexedDB、Blob URL、LRU cache 逻辑应尽量复用。

### 5.3 本地元信息

建议新增一份本地元信息存储，至少记录：

1. `packId`
2. `version`
3. `importTime`
4. `imageCount`
5. `target`
6. `manifest` 原始摘要
7. 是否可用

可用于：

1. 首页显示当前已导入卡图包状态
2. 版本不匹配警告
3. 清除缓存时的状态重置

## 6. UI/UX 设计

### 6.1 首页入口

首页新增至少两个与卡图相关的操作：

1. `导入卡图`
2. `清除卡图`

可选补充：

1. 显示当前卡图包版本
2. 显示是否已导入
3. 显示当前为 SRD 模式 / 已启用图片模式

### 6.2 图片模式开关

未导入卡图包时：

1. 图片模式按钮置灰。
2. 鼠标悬停或点击时提示“当前为 SRD 版本，请先导入卡图包”。
3. 不应发起任何无效图片加载。

已导入卡图包后：

1. 图片模式按钮恢复可用。
2. 用户可自由在图片 / 文字模式间切换。
3. 不强制自动切换为图片模式。

### 6.3 首次进入公告弹窗

首次进入时弹出更新公告弹窗，建议行为：

1. 只在首次进入或公告版本更新后自动弹出。
2. 第一条公告必须写明：
   - 当前为 SRD 版本
   - 默认不包含卡图
   - 如需卡图请自行导入
3. 弹窗内支持渲染 Markdown 内容。
4. 提供“我知道了”关闭按钮。
5. 可选增加“下次不再自动弹出当前版本公告”的记录逻辑。

## 7. 公告系统设计

### 7.1 目录结构

建议新增专用公告目录，例如：

```text
docs/announcements/
├─ 2026-05-srd-release.md
├─ 2026-06-xxxx.md
└─ ...
```

或如果更偏运行时读取，也可以放到：

```text
public/announcements/
├─ index.json
├─ 2026-05-srd-release.md
└─ ...
```

推荐优先考虑运行时更简单的组织方式：

1. 一个索引文件
2. 多个 Markdown 文件

例如：

```json
[
  {
    "id": "2026-05-srd-release",
    "title": "SRD 版本说明",
    "file": "2026-05-srd-release.md",
    "publishedAt": "2026-05-09",
    "priority": 1
  }
]
```

### 7.2 内容维护方式

后续维护公告时只需要：

1. 新增或修改 Markdown 文件
2. 更新索引文件顺序和元信息

这样可以避免：

1. 把公告写死在组件里
2. 每次改公告都改大量 TSX
3. 多版本公告难以维护

### 7.3 首条公告内容要求

第一条公告至少包含：

1. 当前项目已调整为 SRD 版本
2. 默认不再附带卡图
3. 需要卡图请使用首页“导入卡图”功能
4. 原有文字模式仍可直接使用

## 8. 性能约束与 Cloudflare Pages 考量

当前部署在 Cloudflare Pages 免费版，因此本次设计应优先保证：

1. 默认页面体积下降，减少内置图片资源占用。
2. 运行时不依赖远程图片拉取。
3. 图片只在用户本地存在且按需加载。
4. 未导入卡图时，不出现大量 404 图片请求。
5. 继续使用懒加载和缓存策略，避免一次性创建大量 Blob URL。

预期收益：

1. 默认部署包更轻。
2. 首次访问更快。
3. CDN 带宽压力更低。
4. 用户导入卡图后体验接近当前版本。

### 12.2 卡图包导入

1. 导入合法 zip 成功。
2. 导入后本地保存元信息。

## 13. 风险与注意点

1. 不能只“隐藏图片”，必须确保默认发行包本身不再携带相关图片资源。
2. 浏览器不能长期直接读取用户本地文件路径，因此运行时必须转存到 IndexedDB。
3. 现有图片组件较多，不能只改主页面 toggle，需要从底层图片可用性判断入手，避免漏网之鱼。
4. 公告 Markdown 的读取方式要兼顾当前项目的 Next.js 与静态导出方式。
5. 如果未来内置卡数据版本继续更新，需要同步考虑卡图包版本提示策略。

## 14. 暂定验收标准

满足以下条件可认为本次改造完成：

1. 默认发布包中不再包含目标卡图资源。
2. 首次进入会看到 SRD 公告弹窗。
3. 首页存在“导入卡图”入口。
4. 用户导入单个 zip 后可恢复图片体验。
5. 运行时不依赖远程 URL。
6. 未导入卡图时，纯文字模式完整可用。
7. 现有自定义卡包导入系统未受破坏。
8. 公告内容可以通过维护 Markdown 文件持续更新。
